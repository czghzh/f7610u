## A. GPON 关键事实（接手做注册帧前必读）

- **驱动定论**：GPON 驱动是 **`zte_xgpon.ko`**（不是 `zte_xemac2`，也不是 `zte_xemac1`＝EP 层）。
  拉回的模块 `tftp/zte_xgpon.ko`（302 928 B，1948 符号，md5 `6d9c66f2…`）。
  `zte_api_gp_set_ponrcv = ffffffbffc30b5f8`。
- **符号来源**：运行中**原厂活体** `kptr_restrict=0` → `cat /proc/kallsyms`，
  119 525 条 → `work/stock_dump/kallsyms.json`。kernel1/2 分区**加密**，离线提符号没戏。
- **寻址口径**：厂商 `fpga_read_reg(idx)` 是**字下标** → 物理地址 `0x17000000 + idx*4`，跨窗口连续。
  例：`0x16100`→`0x17058400`、`0x16003`→`0x1705800c`、`0x500c0`→`0x17140300`。
- **中断**：`en=read(0x1705800c)` / `st=read(0x17058010)`，**bit2 = PLOAM 到达**。
  清中断**必须 drain**：读 16 字 `0x17058520`（每字 swab32）+ 写 0 到 `0x1705851c`。
  只写 `0x16004=4` 不清标志 → **67 万次/秒中断风暴 → 整机 livelock，只能断电**。
  ISR 必须自带「同一 jiffy >200 次就 `disable_irq_nosync`」的硬保护。
  `0x17200a04/0a08` 是错的中断寄存器（原厂恒 0）。
  `0x17059800` mask 用 `0x1f` 强制清 bit0（O5 实测 `0x16`，我们曾 `0x17`）。
- **OLT 下行报文 48 字节** = 40 正文 + 8 AES-CMIC。`0x17058520` 是**只读窗口**（读不消耗、不清标志，
  可安全反复读）。byte3 = 序号（0.5 s +1）；`0x17058514` = 接收计数；`0x1705851c` bit0 = 有新报文。
  正文固定段含 ASCII **`"HWTC PON"` ⇒ OLT 是华为**。
- **原厂 O5 金矿**（`work/o5_regs.json`，6144 个寄存器；用户回原厂填真注册码上线取的，全程只读）：
  - AES 密钥 `0x17058c80..8c90`，`0x17058c94..8ca4` 是**完全相同的第二份**，各跟 `0x80000000`（bit31 通道使能）。
    密钥是**会话级**的，抄不走也没用；有价值的是**地址、结构、使能位**。
  - `0x17058cb8 = 0x00860086` —— 两个 0x86 字段 = **华为私有 OMCC 模式**（非华为 OLT 应配 `0x00b000b0`）。
  - burst profile `0x17059910` O5=`0x1b01` vs 我们 `0x0f02`（差异最大）；`0x17059800` O5=`0x16`；
    `0x17059400`=0x00090005；`0x1705943c/40`=`0x4009`/`0x4409`（alloc 9）。
  - 另见疑似第二把密钥 `0x170598f8/fc`，`0x170598d8 = 0x534b5957`（ASCII "SKYW"）。
- **两张 256 项表** `0x17058040` / `0x17059200`：**写一个地址会广播铺开 255 个**（首项是独立控制寄存器）。
  第一张已补齐；第二张**故意不填**（疑为 OLT 分配给已注册 ONU 的 alloc-ID，未注册应保默认）。
  `pon_allocmap`（WO，写 1 批量填两张表，**默认不跑**）。
- **厂商发上行**：12 字写 `0x17059b08` 后 `0x17059908=1`。
  TX FIFO `0x17059b08` 多次读**完全不变** ⇒ 静态残影，拿不到原厂上行报文原文。
- **已排除（均有实测）**：pin_mux 差异、MAC 核心 16 实例差异、GEM 16 实例差异、RX 使能位；
  **DBA 区 `0x17180000` 与 MPCP 区 `0x171c0000` 与原厂逐寄存器一致**。
- **推翻记录**（别再踩）：
  - `0x171c0054` 不是 EqD、`0x171c0044` 不是 ONU-ID（§74.1：两边同值且完全静止）。
  - **off15/off16 不是 O5 判据**（§75.2：未注册也会周期性出现 `off15=0x08/off16=0x1f`）。
  - ⇒ **目前不存在任何「注册成功」判据**，只能靠 OLT 侧反应（PLOAM 回包 / DBA 授权变化 / GEM 收包）间接判断。

- ★★★ **注册帧路径（§77 定论，2026-10-18 晚；推翻 §76 的 SN/地址）**：
  - **真 SN = `ZTEG` + `0x0D09D561`**（mtd12 配置 TLV，§72.3；**不是** O5 寄存器反推的 "SKYW"）。
    寄存器：`0x170598d8 = 0x4745445A`、`0x170598dc = 0x0D09D561`（rev 存储）。
  - **开火寄存器 = `0x170599bc`**（索引 0x1666f；`0x1705999c` 是错的，写入不生效）：
    bit0=发送使能、bits[2:1]=onu_id(2)、**bit3=触发**（发完自清）。
  - ★★ **MAC 必须处于 O2 态才发得出去**：`0x17059400` bits[4:0]=2。
    我们驱动写的是 3(O3) → 触发位永不清（硬件拒发）。改 O2 后立即清位。
  - SN 报文 48B：`03 ff 01 00 | SN8 | rand4 | 0×24 | MIC8`；
    MIC=AES-CMAC(key=0x55×16, 0x02‖正文40) + 零位奇偶翻转 → `0x170598f8/fc`（rev）。
    计算脚本 `work/sn_mic.py`。
  - **实测：硬件能发（连发多次触发位都清），但 OLT 无任何回应**（下行只有周期 profile 报文）。
  - `pon_send/pon_fire`（软件路径）对应 **MsgID=0x02 注册应答**，是第二步，不是首发帧。
  - **SN/使能写在易失寄存器，设备重启后必须重写**。
  - ⚠ **批量读寄存器必须用 `work/zxreg`（mmap 单进程）**；shell 循环打 `pon_reg`
    2000+ 次会把网口 RX 打瘫（RX=0），只能重启。

## B. 坑（技术 / 口径 / 写法）

1. **全量构建会改内核 `.config`**：编完必核对 `ZTE_ZX279131_ETH`、`I2C_ZX279133`、`EEPROM_AT24`、`DEVMEM`。
2. `i2cprobe` 地址是**十进制**（0x50 要写 80）；A2 DDM 必须从 **0x60** 起始读；`cat eeprom` 只回前 32 字节。
3. ★ **帧内取字节不能一律 `>>24`**：`swab32` 之后偏移 4n 是**最低**字节、4n+3 是**最高**字节。
   off 3 → `(w[0]>>24)&0xff`；off 15 → `(w[3]>>24)&0xff`；**off 16 → `w[4]&0xff`**。
   曾误写 `>>24`，读出恒 `0xaa` 的假象（像是 grant=170）。
4. ★ **PLOAM bit2 不 drain 就清不掉** → 中断风暴 → 只能断电（见上 A「中断」）。
5. ★ **串口脚本必须单次 open**（`work/ub_boot.py` / `work/uboot_load.py`）：
   bash 里 `printf > /dev/ttyUSB0` 循环会反复 open/close 把 USB 串口复位，日志全空（踩过）。
6. `0x17200a04/0a08` 是错的中断寄存器；`top_crm_base=0x10e10000`，`0x14f0d000` 是 efuse。
7. **运行中禁写**（会断网）：`0x1a2c0004`、`0x17240004`、`0x1a000008/c`、`0x10e20000`（断网过 3 次）。
8. **运行中禁读未知地址**：用户态 `/dev/mem` 读 `0x19000000` 把总线和整机读挂过 ——
   只读走 `work/zxreg`（静态 aarch64 mmap）或 `pon_reg` 白名单；**写必须走 `18000000.pp/zx_poke`**
   （`/dev/mem` 的 mmap 读可以、**写会被丢弃**，写回是缓存假象）。
9. **写法坑**：厂商脚本里 `printf 0x%sn` 经 python 写入落盘会把 `\n` 转成真实换行，
   把 printf 拆成两行 → 设备上报 `08: not found`。用 `echo "0x${v#0x}"`。
10. **环形缓冲显示顺序**：`pon_ploam_all` 的 `#0` 是**最旧**、`#7` 是最新（ring idx 已自增指向下一个待写槽）。
11. **dexec.sh（ubus file exec）2026-10-18 起返回 code 6 无输出**（v9.28 上坏了）→
    设备命令改走 `sshpass -p "" ssh -o StrictHostKeyChecking=no root@192.168.1.1 '<cmd>'`（空密码直连，LuCI 403 是正常的）。
    宿主机串口在 `/dev/ttyUSB0`（CH340 18:26 重插）；**沙箱 /dev 是独立 tmpfs，看不到 ttyUSB0，别在沙箱里直接操作串口**。

12. ★★★ **触发未完成时切 O3 = 整机挂死**（2026-10-18 复现 4 次）。
    `0x170599bc` bit3 置位后在等发送窗口，此时若写 `0x17059400` 回 O3，
    MAC 状态机死锁、总线卡死、串口无任何输出。**只能等看门狗 1–2 分钟复位回原厂**。
    ⇒ 规矩：bit3 没清之前，绝不碰 `0x17059400`。这也是 `run`/`start` 路径必挂的根因。
13. ★★ **O2 后要等 ~45 秒才命中 discovery 窗口**。O2 保持不动、每 5 秒触发一次，
    t0–t8（0–40 s）写 `0xd` 读回恒 `0xd`（没发），t9 以后读回 `0x5`（发出）。
    以前所有「写 0xd 没反应」绝大多数是**窗口没到**，不是 SN/MIC 错。
14. ★ **MIC 不参与发送决策**：`0x170598f8/fc` 清 0 照样能在窗口内发出。
    MIC 只影响 OLT 是否接受，不能拿「发出去了」当 MIC 正确的证据。
15. **`crypto_alloc_shash()` 不能在 work 里调**（会 request_module → 工作队列卡死）。
    在 probe 里分配一次并缓存 tfm；`config-6.18` 要显式开
    `CONFIG_CRYPTO_CMAC=y`，且内核树 `.config` 用 `scripts/config --enable` 同步。
16. **下行报文 MsgID 判据**：`pon_gpon_state` 的 `msgid_hist` 里
    `01`=Upstream_Overhead（0.5 s 一条，常驻）、**`02`=OLT 在问 SN、`03`=已分配 ONU-ID**。
    只有 01 说明 OLT 完全没认；这比任何寄存器都直白。

17. ★★★ **原厂根本不走 `0x170599bc` bit3**（2026-10-19 活体实测，推翻 §77/§78）。
    抖动 LOS 让原厂重注册，16 ms 采样全程 snctl 恒 `0x1`，**bit3 一次都没置位**；
    状态是 **O1 → O3（10 秒）→ O4 → O5，中间没有 O2**。
    ⇒ 之前「O2 态写 0xd 触发 SN」是自己造出来的一条路，原厂不用它。
18. ★★ **OLT 在这个口不发 `02`（Serial_Number_ONU request）**：O1 态保持 60 秒，
    `msgid_hist` 只有 `01`，state 也不会自己跳到 O3。原厂进 O3 是**软件超时**驱动的。
19. ★ **`0x1705947c` bit22 = 未注册标志**：未注册 `0x43FF0000`，拿到 alloc 后 `0x03FF0000`。
20. **U-Boot tftp 连续失败会耗尽包缓冲池**（串口刷 `alloc bp failed`），之后所有 tftp 都失败；
    只能 `reset` 清（`work/ub_reset_grab.py`：发 reset 后单次 open 喂键抢提示符）。

21. ★★★ **这台设备是 XG-PON，不是 GPON**（2026-10-19 用户确认 + 三条硬证据）。
    - 光模块 A0 名称 `ZTE_XEPON_AS`；
    - PLOAM 是 **48 字节**（GPON 是 13 字节，XG-PON 才是 48）；
    - 下行 `03ff01xx …` 的 `byte2=0x01` 是 **XG-PON Profile**，不是 GPON 的 Upstream_Overhead。
    ⇒ 上行注册帧 MsgID 应为 **0x02（Registration）**，不是 GPON 的 0x01（Serial_Number）。
    ⇒ 之前 §1–§80 所有"GPON 注册"的推断都建立在错误前提上，别再照着做。
    ⇒ 协议参考：`/home/wen/WorkBuddy/zx/pon-drivers-ref/airoha-xpon/`（`ploam.c` / `xgpon.c` / `crypto.c`）。

22. ★★ **整个 0x17000000 的 6144 个寄存器，我们与原厂 O5 只差 32 个**（全是注册后的状态位）。
    ⇒ 别再往 MAC 配置上找原因了，配置已经一致。
    真正的差异只剩 SerDes/CRM 两处：`0x10e40058`（原厂 `0x03E23333` / 我们 `0xB3E23333`）、
    `0x10e10050`（原厂 `0x00DFF3FF` / 我们 `0x001F8070`）。
23. ★ **U-Boot 灌机两个坑**：
    - tftp 反复失败后 `alloc bp failed` 不可逆（连 ping 都不行），warm reset 也清不掉；
      最可靠是走冷启动路径（原厂 telnet `reboot -f` → 抢 U-Boot → tftp）。
    - **中断过 autoboot 的 U-Boot 无法手动启动原厂**：`bootcmd` 是 `bootm 0x88000240`，
      那个镜像是 autoboot 流程负责加载的，中断后手动 bootm 报 `B't get kernel image`。
      ⇒ 回原厂的办法：串口 `reset` 后**完全不喂键**，等 95 秒（`work/ser_reset_nokey.py`）。

24. ★★★ **`pon_bwmap` 节点测量口径（2026-10-20 实测，别再用错）**：
    - 子命令**只有** `rec` / `stop` / `dump` 三个字符串，经 `sscanf("%15s")` 解析。
      **`echo 1 > pon_bwmap` 是静默失败的**（`sscanf` 拿到 "1" → 三个都不匹配 → `-EINVAL`，
      busybox 有时只吐 `write error: Invalid argument`，有时完全无输出）⇒ 千万别用 `echo 1` 触发。
      正确调用：`echo dump > .../pon_bwmap`。
    - ★ **dmesg 是累积的**：每跑一次 `dump` 就往 dmesg 追加 512 行 `bwmap[N] ...`。
      若用 `dmesg | grep bwmap | grep alloc=9 | wc -l`，统计的是**历史上所有 dump 的总和**，
      不是单次快照 —— 会把 4 条/次误读成几十条（本会话 2026-10-20 就这样误判过一次，
      口头报了"37 条 alloc=9"，实际单次只有 4 条）。
      单次口径必须 `dmesg | grep 'bwmap\[' | tail -512 | ...`（或先 `dmesg | wc -l` 记行号再算增量）。
    - 实测单次 dump（512 行，含空跳过）分布：**~505 条 `alloc=1023`（发现窗口）+ 仅 4 条 `alloc=9`**。
      ⇒ **"OLT 基本不给 ONU 9 常态上游授权（alloc=9）"这个结论是对的**；alloc=9 非绝对 0，但占比 <1%。
    - `alloc` 字段 = `w1 & 0x3fff`；`w0` 是授权块大小/标志：`w0=00000004` PLOAM 小槽、
      `w0=70064000` 数据块、发现窗口多为 `alloc=1023`。
